# 題材設定

今回題材にするのは、2 次元フライトシューティングゲームの AI です。

ゲームとしては、2D 平面上を戦闘機が移動し、敵機を追尾しながらミサイルを発射して撃墜を狙うというものです。厳密な航空力学シミュレーションではなく、あくまで「空戦っぽい挙動をするゲーム」として実装しています。単に今回の学習用に作ったプロトタイプなので、ゲーム自体は正直つまんないです。

このテーマにした理由は、今年発売予定の ACE COMBAT 8 が待ちきれなかったので、戦闘機の AI を作ってエース気分を味わおうと思ったからです。あと、`Aircraft` 最初の 2 文字が `AI` なので今回のテーマにちょうどいい気がしました。

今回は実際のゲーム開発を想定し、ゲームロジックの実装は C++ で行いました。

プレイヤーや AI が操作する機体は次の 3 つの入力を毎フレーム受け取ります。

```cpp
struct FighterInput
{
    double acceleration; // 加減速 [-1.0, 1.0]
    double turn;         // ヨーイング [-1.0, 1.0]
    bool fire;           // ミサイル発射
};
```

各機体は加減速、旋回運動、ミサイル発射入力が行えます。ミサイル発射後は一定時間のクールダウンが発生するため、毎フレーム無限にミサイルを撃てるわけではありません。ミサイルは簡易的なホーミング機能もあります。

戦闘機の状態は以下のような構造体で表現しています。

```cpp
struct FighterState
{
    int teamId;      // 0 だったら自軍、1 だったら敵軍
    int memberId;    // チーム内識別 ID (0-origin)
    Vec2 position;   // 戦場内の座標
    double yaw;      // 機体の向き
    double speed;    // 機体の速度
    // (中略)
};
```

戦場全体は `BattlefieldContext` で表現します。

`BattlefieldContext` の更新は、以下の関数を毎フレーム呼び出して行います。この更新関数では描画は行いません。

```cpp
void UpdateBattlefield(
    BattlefieldContext& context,
    const std::array<FighterInput, FighterCount>& inputs,
    double deltaTime
);
```

`BattlefieldContext` の描画は別途 `BattlefieldRenderer` というクラスに切り分けました。`BattlefieldContext` は戦場の状態だけを持つ構造体であり、描画関連の要素を一切持ちません。これにより、描画無しでゲームロジックを進めることが出来るようになるので、大量のエピソードを走らせる強化学習が回りやすくなります。

今回、個人的な好みで描画には Siv3D というエンジンを使用しました。Siv3D は C++ で手軽に 2D/3D 描画や入力処理を扱えるライブラリで、今回のような小規模なゲームプロトタイプを作るにはかなり便利です。

また、描画については GPU を使った通常のハードウェアレンダリングだけでなく、CPU のみで可能なソフトウェアレンダリングにも対応させました。今回学習に利用した計算機環境では GPU は使えるものの、GUI アプリケーションを表示するディスプレイ環境が用意されていなかったためです。手元の開発環境では標準のハードウェアレンダリング (OpenGL) で可視化し、学習用の計算機環境では確認用に必要に応じてソフトウェアレンダリングを使う形にしました。Siv3D のレンダリングバックエンドに "DirectX", "OpenGL" と並んで "ソフトウェアレンダリング" というオプションがあるわけではないのですが、今回はエンジン側を改造せずにアプリケーション側で描画処理を一段階抽象化することで行っています。

また、描画については、GPU を使った通常のハードウェアレンダリングだけでなく、CPU のみで動作するソフトウェアレンダリングにも対応させました。今回学習に利用した計算機環境では GPU 自体は利用できるものの、GUI アプリケーションを表示するためのディスプレイ環境が用意されていませんでした。そのため、手元の開発環境では標準のハードウェアレンダリング (今回は OpenGL バックエンド) を使って可視化し、学習用の計算機環境では必要に応じてソフトウェアレンダリングで確認用の画像を出力する形にしました。実装について、Siv3D のレンダリングバックエンドに `DirectX` や `OpenGL` と並んで `ソフトウェアレンダリング` という選択肢があるわけではないのですが、今回は Siv3D 本体を改造するのではなく、アプリケーション側で描画処理を一段階抽象化して通常の画面描画と確認用のソフトウェア描画を切り替えられるようにしています。

学習時には、Python 側から C++ のゲームロジックを呼び出し、現在の状態を取得します。その状態を機械学習用の観測ベクトルに変換し、PyTorch で作成したニューラルネットワークに入力します。ニューラルネットワークは `FighterInput` それぞれのパラメータ確率分布を出力します。

サンプルした行動を再び C++ 側に渡してゲームを 1 ステップ進め、得られた報酬をもとに学習を進めます。

大まかな構成をまとめると、次のようになります。

```txt
C++ 側: ゲームロジック
  ├─ 機体やミサイルの状態更新などのシミュレーション
  ├─ Siv3D による描画
  └─ Python から呼び出すためのバインディング

Python 側: 学習
  ├─ 観測の整形
  ├─ 方策ネットワーク
  ├─ 報酬計算
  ├─ 学習ループ
  └─ 評価・可視化
```

今回の記事では、この 2D フライトシューティングゲームを題材にして C++ で実装したゲームロジックを Python から操作し、深層強化学習によって AI を学習させる流れを見ていきます。


# C++ ゲームロジックを nanobind を用いて Python から扱う方法について

まず初めに、どうして C++ だけで完結させずに Python を使うのかについて整理します。

理由は単純で、機械学習ライブラリ (今回は PyTorch) を使うためです。機械学習の実装は自前で素直な実装出来ますが、世の中で広く使われているライブラリよりも優れたパフォーマンスの実装にするには非常に困難です。機械学習は 1 回の学習の結果が出るまで 1 日では終わらないことも多く、その上でパラメータやモデル設計の試行錯誤が何度も必要です。そのため、PyTorch のような成熟して優れた実行性能のライブラリを使うことにより、限られた時間より多くの実験を試すことが可能になります。

C++ と Python を連携させる方法はいくつかあります。大まかには次のような選択肢が考えられます。

1. C++ 側のプログラムを外部プロセスとして起動し、標準入出力やソケットを介して Python と通信する

2. C++ 側のプログラムを外部プロセスとして起動し、メモリ領域を Python と共有する (共有メモリ)

3. C++ の型や関数を Python が扱えるようにバインディングし、Python から C++ の処理を呼び出す

最小構成のイメージは次のようになります。

```cpp
#include <nanobind/nanobind.h>

namespace nb = nanobind;

int add(int a, int b)
{
    return a + b;
}

NB_MODULE(toy_acai_core, m)
{
    m.def("add", &add);
}
```

これをビルドすると、Python 側からは次のように呼び出せます。

```python
import toy_acai_core

print(toy_acai_core.add(1, 2))
```

今回の実装では、足し算関数ではなく、戦場の状態を表す `BattlefieldContext` や、各機体への入力を表す `FighterInput` などを Python 側へ公開しています。

方針としては、C++ 側に `BattlefieldEnv` のような強化学習専用の環境クラスを新しく作るのではなく、既存のゲームロジックに近い単位をそのまま Python から扱えるようにしています。つまり、Python 側で `BattlefieldContext` を作成し、それを `init_battlefield()` で初期化し、毎フレーム `update_battlefield()` に入力を渡して更新する構成です。

Python 側から見た基本的な使い方は次のようになります。

```python
import toy_acai_core as core

battlefield = core.BattlefieldContext()
core.init_battlefield(battlefield)

inputs = [
    core.FighterInput(0.0, 0.0, False)
    for _ in range(core.FIGHTER_COUNT)
]

core.update_battlefield(battlefield, inputs, 1.0 / 60.0)
```

`BattlefieldContext` は戦場全体の状態を持つオブジェクトです。内部には、戦闘機の状態、ミサイルの状態、命中イベントなどが含まれます。

`FighterInput` は、各機体に対する 1 フレーム分の入力です。

```cpp
struct FighterInput
{
    double acceleration;
    double turn;
    bool fire;
};
```

Python 側では次のように生成できます。

```python
fighter_input = core.FighterInput(
    acceleration=1.0,
    turn=0.2,
    fire=False,
)
```

`update_battlefield()` には、全機体分の `FighterInput` を渡します。今回の実装では、入力の個数が `FIGHTER_COUNT` と一致していない場合はエラーにするようにしています。これにより、「一部の機体の入力を渡し忘れたままシミュレーションが進む」といった事故を防げます。

C++ 側のバインディングは、概略としては次のような形です。

```cpp
NB_MODULE(toy_acai_core, m)
{
    m.attr("FIGHTER_COUNT") = toy_acai::FighterCount;
    m.attr("MAX_MISSILE_COUNT") = toy_acai::MaxMissileCount;

    nb::class_<toy_acai::FighterInput>(m, "FighterInput")
        .def(nb::init<>())
        .def(nb::init<double, double, bool>(),
             "acceleration"_a, "turn"_a, "fire"_a)
        .def_rw("acceleration", &toy_acai::FighterInput::acceleration)
        .def_rw("turn", &toy_acai::FighterInput::turn)
        .def_rw("fire", &toy_acai::FighterInput::fire);

    nb::class_<toy_acai::BattlefieldContext>(m, "BattlefieldContext")
        .def(nb::init<>())
        .def(nb::init<const toy_acai::BattlefieldContext&>())
        .def_prop_ro("fighters", /* ... */)
        .def_prop_ro("missiles", /* ... */)
        .def_prop_ro("hit_events", /* ... */);

    m.def("init_battlefield", &toy_acai::InitBattlefield, "context"_a);

    m.def("update_battlefield",
        [](toy_acai::BattlefieldContext& context,
           nb::iterable inputs,
           double deltaTime)
        {
            toy_acai::UpdateBattlefield(
                context,
                MakeFighterInputs(inputs),
                deltaTime
            );
        },
        "context"_a, "inputs"_a, "delta_time"_a);
}
```

ここで重要なのは、`update_battlefield()` 自体に機械学習用の処理を書いていないことです。バインディング層は、あくまで Python から C++ のゲームロジックを呼び出すための薄い橋渡しにしています。

ゲームの状態更新そのものは、通常の C++ 関数である `UpdateBattlefield()` が担当します。Python 側は、入力を作ってその関数を呼び出すだけです。

この構成にしておくと、通常のゲーム実行と強化学習用の実行で、同じシミュレーションロジックを使い回せます。つまり、C++ 側のゲームとして動かしたときと、Python から学習環境として動かしたときで、機体の移動やミサイルの挙動が分岐しにくくなります。

また、`BattlefieldContext` の中身は Python 側から参照・変更できるようにしています。例えば、機体一覧には `fighters` からアクセスできます。

```python
fighter = battlefield.fighters[0]

print(fighter.position.x)
print(fighter.position.y)
print(fighter.yaw)
print(fighter.speed)
```

必要であれば、Python 側から直接値を書き換えることもできます。

```python
battlefield.fighters[0].position.x = 120.0
battlefield.fighters[0].position.y = 240.0
battlefield.fighters[0].yaw = 0.0
battlefield.fighters[0].speed = 100.0
```

強化学習の実験では、初期配置をランダム化したり、カリキュラム学習用に敵機の状態を変更したりしたくなる場面があります。そのため、Python 側から状態をある程度触れるようにしておくと便利です。

一方で、何でも Python 側から自由に書き換えられるようにすると、C++ 側の不変条件を壊しやすくなります。例えば、本来なら同時に更新されるべき値の片方だけを書き換えてしまうと、ゲーム状態として不自然な状態が生まれる可能性があります。このあたりは、実験のしやすさと安全性のトレードオフになります。

今回のようなプロトタイプでは、学習側で色々試したかったため、比較的直接的に状態へアクセスできる設計にしています。

学習ループでは、次のような流れで C++ 側のシミュレーションを進めます。

```python
battlefield = ctx.battlefield

for step in range(max_step_count):
    observation = build_observation(battlefield)
    obs_tensor = observation_to_tensor(observation).to(device)

    action_tensor, log_prob = policy.sample_action(obs_tensor)
    acceleration, turn, fire = action_tensor.detach().cpu().tolist()

    inputs = [
        core.FighterInput()
        for _ in range(core.FIGHTER_COUNT)
    ]

    inputs[0] = core.FighterInput(
        acceleration,
        turn,
        fire >= 0.5,
    )

    core.update_battlefield(
        battlefield,
        inputs,
        constants.SIMULATION_DELTA_TIME,
    )
```

ここでは、C++ 側の `BattlefieldContext` から現在の状態を読み取り、Python 側で観測ベクトルを作っています。その観測を PyTorch の方策ネットワークへ入力し、出力された行動を `FighterInput` に変換して、再び C++ 側へ渡します。

つまり、1 フレームごとに次の処理を繰り返します。

```txt
C++ の BattlefieldContext
  ↓
Python 側で観測ベクトルを作成
  ↓
PyTorch の方策ネットワークで行動を決定
  ↓
FighterInput として C++ 側へ渡す
  ↓
UpdateBattlefield() で 1 ステップ進める
```

この構成により、ゲームロジックは C++ のまま、学習アルゴリズムは Python / PyTorch で書けるようになります。

また、`BattlefieldContext` にはコピーコンストラクタも公開しています。これにより、Python 側で現在の戦場状態をコピーできます。

```python
saved_battlefield = core.BattlefieldContext(battlefield)
```

これは強化学習の実験でかなり便利です。例えば、ミサイルに当たって死んだ直前の状態を保存しておき、別の回避行動を試す、といったことができます。

実際に、過去の状態を保存しておいて、後から別の入力でシミュレーションをやり直すような処理にも使えます。

```python
past_battlefield = core.BattlefieldContext(battlefield_history[0])

override_inputs = copy_inputs(inputs)
override_inputs[0] = core.FighterInput(1.0, -1.0, False)

core.update_battlefield(
    past_battlefield,
    override_inputs,
    constants.SIMULATION_DELTA_TIME,
)
```

強化学習では、「この行動を選んだから死んだのか」「別の行動なら避けられたのか」を調べたくなることがあります。そのため、ゲーム状態をコピーして巻き戻せるようにしておくと、教師データ生成やデバッグに使いやすくなります。

描画についても、Python 側から必要に応じて呼び出せるようにしています。

ただし、学習中に毎フレーム描画すると非常に重くなるため、通常の学習ループでは描画を行いません。評価時やデバッグ時だけ `BattlefieldRenderer` を使い、画像バッファへレンダリングするようにしています。

Python 側からは、次のような形で使えます。

```python
renderer = core.BattlefieldRenderer()
renderer.enable_render_to_image_buffer(core.Size(640, 360))

renderer.update(battlefield, 1.0 / 60.0)
renderer.render(battlefield)

frame = renderer.image_buffer()
```

`image_buffer()` は RGBA の画像配列を返すため、Python 側で `PIL.Image.fromarray()` などに渡して、PNG や GIF として保存できます。

このように、学習時はヘッドレスに高速実行し、必要なときだけ画像として可視化できるようにしています。

今回の構成をまとめると、次のようになります。

```txt
C++ 側:
  ├─ BattlefieldContext が戦場状態を持つ
  ├─ UpdateBattlefield() が 1 フレーム分の更新を行う
  ├─ FighterInput が各機体への入力を表す
  ├─ BattlefieldRenderer が必要に応じて描画する
  └─ nanobind でこれらを Python へ公開する

Python 側:
  ├─ BattlefieldContext を作成する
  ├─ init_battlefield() で初期化する
  ├─ 現在状態から観測ベクトルを作る
  ├─ PyTorch のネットワークで行動を決める
  ├─ FighterInput を作る
  └─ update_battlefield() で C++ 側のシミュレーションを進める
```

この設計の良いところは、C++ 側に機械学習フレームワークの都合を入れすぎずに済むことです。

C++ 側はあくまで「ゲームの状態を持つ」「入力に応じて状態を進める」「必要なら描画する」という責務に集中します。一方、Python 側では、観測設計、報酬設計、ニューラルネットワーク、学習ループを自由に変更できます。

強化学習では、観測や報酬の設計を何度も変えることになります。そのたびに C++ 側をビルドし直すのはかなり面倒です。ゲームロジックそのものは C++ に置き、実験の変化が激しい部分を Python 側に寄せることで、試行錯誤しやすくなりました。

もちろん、nanobind を使えば何でも自動で解決するわけではありません。C++ オブジェクトの寿命、参照を返すかコピーを返すか、Python 側からどこまで内部状態を変更できるようにするか、といった点は慎重に設計する必要があります。

それでも、今回のように「C++ で書いたゲームロジックを Python から何度も呼び出して、PyTorch で学習する」という用途にはかなり相性が良いと感じました。
