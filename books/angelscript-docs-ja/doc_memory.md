title: "メモリ管理 (Memory management)"
---

この記事では AngelScript のメモリ管理について詳しく説明します。ほとんどの開発者が知る必要があるよりも詳しい内容ですが、AngelScript をより正確に評価するためにどのように機能するかを正確に知りたい方もいるでしょう。

## メモリ管理の概要 (Overview of the memory management)

AngelScript は参照カウント (reference counting) とガベージコレクション (garbage collection) の両方を使用するハイブリッドな方法を採っており、参照カウントがメインの方法で、ガベージコレクションは循環参照を解決する必要がある場合のバックアップとしてのみ使用されます。

この設計が選ばれたのは、参照カウントがスクリプトエンジンとアプリケーション間でオブジェクトを受け渡しながら、生存しているオブジェクトを追跡し続ける最も簡単な方法だからです。もし純粋なガベージコレクションを使用した場合、スクリプトエンジンはスクリプトオブジェクトが保存される可能性のあるアプリケーションのメモリ空間全体を把握しなければなりません。そうしないと、オブジェクトがまだ生存しているかどうかがわからなくなります。

ガベージコレクターは、例えばメンバー変数として自身と同じ型へのハンドルを持つオブジェクトのように、それ自身や他のオブジェクトとの循環参照を形成する可能性があるオブジェクト型にのみ使用されます。そのようなオブジェクトが作成されるたびに、ガベージコレクターはオブジェクトを追跡できるよう通知を受けます。

ガベージコレクターはエンジンによって自動的に実行されますが、アプリケーションは実行タイミングをより細かく制御するために手動で行うことを選択することもできます。ガベージコレクターはインクリメンタル (段階的) であるため、残りの処理を長期間停止させることなく、アプリケーション実行全体を通じて小さなステップで実行することができます。

参照: [ガベージコレクション](./doc_gc)

## 参照カウントのアルゴリズム (Reference counting algorithm)

組み込みのスクリプトオブジェクトはすべて自動的に参照カウントされ、スクリプトエンジンの外部でオブジェクトへの参照を保存する場合は、アプリケーションが適切に `AddRef` と `Release` メソッドを呼び出す必要があるだけです。

アプリケーションが登録したオブジェクトは、参照カウントされる場合とされない場合があります。参照カウントされるべきものは、AngelScript が参照カウントの変更をオブジェクトに通知できるよう、`ADDREF` と `RELEASE` の振る舞いを実装しなければなりません。アプリケーションは参照カウンター自体を管理し、オブジェクトへの参照がなくなった時にメモリを解放する必要があります。これは通常、参照カウントを保持するために整数型のメンバー変数をオブジェクト構造体自体に持たせることで行われます。参照カウンターを保持するための別の構造体で実装することもできますが、各変更時に参照カウンターを検索しなければならないため、余分なオーバーヘッドが加わります。

参照: [型の登録](./doc_register_type)

## ガベージコレクターのアルゴリズム (Garbage collector algorithm)

参照カウントだけでは不十分なシナリオを処理するために使用されるガベージコレクターは、以下のアルゴリズムを使用します。

1. **ガベージの破棄 (Destroy garbage):** 参照が1つしかないオブジェクトをすべて解放します。この参照はGC自体が保持しているため、他に誰もそのオブジェクトを参照していないことが分かります。

2. **カウンターのクリア (Clear counters):** 残りのオブジェクトのGCカウンターをクリアします。このカウンターは、GCから到達可能なオブジェクトへの参照をカウントするために使用されます。同時に、ガベージコレクターの実行中に参照が変化したかどうかを検出できるように、オブジェクトにフラグも立てられます。このフラグは参照カウンターをインクリメントまたはデクリメントした際に自動的にクリアされます。

3. **GC参照のカウント (Count GC references):** GC内の各オブジェクトに対して、そのオブジェクトが参照を保持している全オブジェクトのGCカウンターをインクリメントするよう指示します。これはまだフラグが立っているオブジェクトに対してのみ行われます。なぜなら、もしフラグが既にクリアされていれば、それがアプリケーションによって参照されたことが分かるため、そのオブジェクトと、それが参照を保持しているすべてのオブジェクトが生存していると見なすことができるからです。

4. **生存オブジェクトのマーク (Mark live objects):** GC内のすべてのオブジェクトの中で、フラグが立っていない、またはGCカウントが参照カウンターと等しくないオブジェクトのリストを構築します。これらは生存していると見なされるオブジェクトです。リスト内の各オブジェクトに対して、そのオブジェクト内のすべての参照も（まだリストにない場合は）リストに追加します。リストがトラバース（巡回）されるにつれて新しいオブジェクトが追加され、これらのオブジェクトもその参照がリストに追加されます。このようにして参照の連鎖をたどり、生存しているすべてのオブジェクトを収集します。

5. **マークされていないオブジェクトの検証 (Verify unmarked objects):** GC内のオブジェクトのリストをもう一度通過し、生存としてマークされなかったオブジェクトのいずれかでフラグがクリアされていないかどうかを確認します。もしそうであれば、「生存オブジェクトのマーク」のステップを再実行します。

6. **循環参照の解除 (Break circular references):** この時点で生存していることがマークされていないすべてのオブジェクトは、到達不可能な循環参照に関与しており、破棄されなければなりません。オブジェクトをそれらが保持する参照を解放するよう指示することでオブジェクトは破棄され、循環参照が解除されます。すべての循環参照が解除されると、GCルーティン全体が再起動され、オブジェクトが解放されます。死んでいるオブジェクトがなければ、GCは終了します。

すべてのステップはインクリメンタル（段階的）であり、つまりガベージコレクションを続ける前にアプリケーションとスクリプトが実行できるよう中断することができます。ステップ 1 はサイクル中のいつでも個別に実行することもでき、これにより循環メモリに関与していないオブジェクトのメモリを、検出サイクルが完了するのを待たずに解放することができます。

GC には新世代 (new generation) と旧世代 (old generation) の概念もあります。すべての新しいオブジェクトは新世代に配置されます。この世代では、上記の「ガベージの破棄」ステップという些細なガベージコレクションのみが行われます。新世代のオブジェクトが破棄されずに数回のイテレーションを生き残ると、旧世代に移動します。旧世代では、完全なガベージコレクションのアルゴリズムが実行されます。

この新世代と旧世代の分割は、循環参照を検出するために GC が行う処理量を減らし、アプリケーションのパフォーマンスを向上させます。

参照: [GC 対応オブジェクトの登録](./doc_gc_object)

## メモリヒープ (Memory heap)

デフォルトでは、AngelScript はメモリを割り当てる際に標準の `malloc` と `free` グローバル関数を通じてアクセスされるメモリヒープを使用します。通常これは AngelScript がアプリケーションとメモリヒープを共有することを意味しますが、もし AngelScript ライブラリが DLL または共有オブジェクトとしてコンパイルされている場合、ヒープは実際にはアプリケーションのヒープとは別になる可能性があります。

一部のアプリケーションは標準の C/C++ ライブラリが提供しないようなメモリヒープへの追加の制御を必要とします。これは、メモリが限られており、断片化や多数の小さな割り当てによるスペースの無駄を許容できないコンソール向けビデオゲームではよくあることです。AngelScript はこのようなアプリケーションもサポートしており、ライブラリにカスタムのメモリ割り当てルーティンを登録することが可能で、AngelScript が使用するメモリを正確にアプリケーションが制御できるようにします。

参照: [asSetGlobalMemoryFunctions](#asSetGlobalMemoryFunctions)
