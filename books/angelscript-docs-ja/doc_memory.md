本稿では、AngelScript のメモリ管理メカニズムについて詳細に解説します。多くの開発者にとっては必要以上に踏み込んだ内容かもしれませんが、ライブラリの内部動作を正確に把握し、AngelScript をより深く評価したい方向けの情報です。

## メモリ管理の概要 (Overview of the memory management)

AngelScript は、参照カウント（Reference Counting）とガベージコレクション（Garbage Collection）を組み合わせたハイブリッド方式を採用しています。参照カウントを主軸とし、循環参照の解決が必要な場合にのみ、バックアップとしてガベージコレクション（GC）が機能します。

この設計が選ばれたのは、参照カウントがスクリプトエンジンとアプリケーション間でオブジェクトをやり取りしつつ、生存しているオブジェクトを追跡する最も簡潔な方法だからです。もし純粋なガベージコレクションのみを採用した場合、スクリプトエンジンは、スクリプトオブジェクトが保持される可能性があるアプリケーション側の全メモリ空間を把握しなければならず、管理が非常に困難になります。

ガベージコレクターは、自身または他のオブジェクトとの間で循環参照を形成する可能性がある型（例：自身と同じ型へのハンドルをメンバに持つオブジェクトなど）に対してのみ機能します。そのようなオブジェクトが生成されるたびに、エンジンはガベージコレクターへ通知し、追跡対象に加えます。

ガベージコレクターはエンジンによって自動的に実行されますが、実行タイミングを制御するためにアプリケーション側から手動で呼び出すことも可能です。ガベージコレクターはインクリメンタル（段階的）に動作するため、実行を小さなステップに分割でき、アプリケーションの動作を長時間止めることなく並行して処理を進めることができます。

参照: [ガベージコレクション](./doc_gc)

## 参照カウントのアルゴリズム (Reference counting algorithm)

組み込みのスクリプトオブジェクトはすべて自動的に参照カウントされ、スクリプトエンジンの外部でオブジェクトへの参照を保存する場合は、アプリケーションが適切に `AddRef` と `Release` メソッドを呼び出す必要があるだけです。

アプリケーションが登録したオブジェクトは、参照カウントされる場合とされない場合があります。参照カウントされるべきものは、AngelScript が参照カウントの変更をオブジェクトに通知できるよう、`ADDREF` と `RELEASE` の振る舞いを実装しなければなりません。アプリケーションは参照カウンター自体を管理し、オブジェクトへの参照がなくなった時にメモリを解放する必要があります。これは通常、参照カウントを保持するために整数型のメンバー変数をオブジェクト構造体自体に持たせることで行われます。参照カウンターを保持するための別の構造体で実装することもできますが、各変更時に参照カウンターを検索しなければならないため、余分なオーバーヘッドが加わります。

参照: [型の登録](./doc_register_type)

## ガベージコレクターのアルゴリズム (Garbage collector algorithm)

参照カウントだけでは不十分なシナリオ（循環参照）を解決するために、ガベージコレクターは以下のアルゴリズムを使用します。

1. **ガベージの破棄 (Destroy garbage):** 参照カウントが 1 であるオブジェクトをすべて解放します。この「1」は GC 自身が保持している参照であるため、他からは一切参照されていない（＝破棄可能である）ことが保証されています。

2. **カウンターのクリア (Clear counters):** 残っているオブジェクトの GC カウンターをクリアします。このカウンターは、GC から到達可能なオブジェクトへの参照をカウントするために使用されます。同時に、ガベージコレクターの実行中に参照が変化したかどうかを検出できるよう、オブジェクトにフラグを立てます。このフラグは、アプリケーションによって参照カウンターがインクリメントまたはデクリメントされた際に自動的にクリアされます。

3. **GC参照のカウント (Count GC references):** GC 内の各オブジェクトに対して、そのオブジェクトが保持しているすべての参照先オブジェクトの GC カウンターをインクリメントするよう指示します。これはまだフラグが立っているオブジェクトに対してのみ行われます。なぜなら、フラグがクリアされていれば、それがアプリケーションによって参照されたことが分かり、そのオブジェクトと、それが参照しているすべてのオブジェクトが生存していると見なせるからです。

4. **生存オブジェクトのマーク (Mark live objects):** GC 内のすべてのオブジェクトの中で、フラグが立っていない、もしくは GC カウントが合計参照カウントと一致しないオブジェクトのリストを構築します。これらは生存していると見なされるオブジェクトです。リスト内の各オブジェクトに対し、そのオブジェクト内のすべての参照先も（まだリストにない場合は）リストに追加します。このトラバース（巡回）によってリストは拡張され、生存しているすべてのオブジェクトが収集されます。

5. **マークされていないオブジェクトの検証 (Verify unmarked objects):** GC 内のオブジェクトリストをもう一度走査し、生存とマークされなかったオブジェクトの中でフラグがクリアされたものがないかを確認します。もしあれば、「生存オブジェクトのマーク」のステップを再実行します。

6. **循環参照の解除 (Break circular references):** ここまでのステップで生存が確認されなかったオブジェクトは、到達不可能な循環参照の一部であるとみなされ、破棄対象となります。これらのオブジェクトに対し、保持している参照を解放するよう指示することで循環参照を断ち切ります。すべての循環参照が解除された後、GC ルーチンが再始動し、対象のオブジェクトがメモリから解放されます。破棄すべきオブジェクトがなくなれば、GC サイクルは終了します。

すべてのステップはインクリメンタル（段階的）に実行されるため、ガベージコレクションを継続する前に、アプリケーションやスクリプトの実行を優先して中断することができます。ステップ 1 はサイクル中のいつでも個別に実行可能であり、これにより循環参照に関与していないオブジェクトのメモリを、検出サイクルの完了を待たずに即座に解放できます。

GC には「新世代（New Generation）」と「旧世代（Old Generation）」の概念があります。新しく生成されたオブジェクトはすべて新世代に配置されます。新世代では、上記の「ガベージの破棄」ステップのみという非常に軽量な GC が行われます。新世代のオブジェクトが破棄されずに数回のイテレーションを生き残ると、旧世代に移動します。旧世代では、フル・ガベージコレクション・アルゴリズムが実行されます。

この新世代と旧世代の分離により、循環参照を検出するための GC の負荷が軽減され、アプリケーション全体のパフォーマンスが向上します。

参照: [GC 対応オブジェクトの登録](./doc_gc_object)

## メモリヒープ (Memory heap)

デフォルトでは、AngelScript はメモリを割り当てる際に標準の `malloc` と `free` グローバル関数を通じてアクセスされるメモリヒープを使用します。通常これは AngelScript がアプリケーションとメモリヒープを共有することを意味しますが、もし AngelScript ライブラリが DLL または共有オブジェクトとしてコンパイルされている場合、ヒープは実際にはアプリケーションのヒープとは別になる可能性があります。

一部のアプリケーションは標準の C/C++ ライブラリが提供しないようなメモリヒープへの追加の制御を必要とします。これは、メモリが限られており、断片化や多数の小さな割り当てによるスペースの無駄を許容できないコンソール向けビデオゲームではよくあることです。AngelScript はこのようなアプリケーションもサポートしており、ライブラリにカスタムのメモリ割り当てルーティンを登録することが可能で、AngelScript が使用するメモリを正確にアプリケーションが制御できるようにします。

参照: `asSetGlobalMemoryFunctions`
